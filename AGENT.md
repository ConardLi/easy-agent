# AGENT.md

This file provides guidance to AI agents when working with code in this repository.

## What this project is

Easy Agent is a **terminal-native agentic coding CLI** published as the `eagent` npm package. It installs the `eagent` command and the `easy-agent` long alias.

- Runtime: Node 22+, ESM, strict TS, target ES2022, JSX `react-jsx`
- TUI: React 19 + Ink 7 (no web framework)
- Package manager: **npm** (`package-lock.json` is canonical — no pnpm/yarn/bun lockfiles)
- Single published package. `apps/desktop/` is the Electron desktop client: a separate npm project with its own lockfile and Biome config, not an npm workspace. The root `npm run lint` skips `apps/`, and `.github/workflows/desktop.yml` checks it

The code is organized into five broad layers:

1. **Interaction** — Ink/React terminal UI (`src/ui/`)
2. **Orchestration** — the session SDK (`src/sdk/`: `AgentRuntime` bootstraps a workspace, `AgentSession` runs turns, records the transcript, and brokers permission/plan/question requests), multi-turn engine and slash commands (`src/core/queryEngine.ts`, `src/commands/`), persistence (`src/session/`). Conversation state lives in session scopes (`src/state/sessionScope.ts`); frontends (`src/ui/`, `src/entrypoint/`, `src/rpc/`, `src/acp/`) reach it only through `src/sdk/`
3. **Agentic loop** — reason → tool call → observe (`src/core/`, `src/agents/`)
4. **Tooling** — file/shell/search/web/MCP/local tools with permissions and sandboxing (`src/tools/`, `src/permissions/`, `src/sandbox/`, `src/services/mcp/`)
5. **Model communication** — provider profiles and streaming LLM I/O over `llm-bridge` (`src/services/api/`)

The numbered roadmap is complete through **Stage 36**. The `eagent` package is published on npm, and the post-publication registry cold check passes.

## Commands (the non-obvious ones)

Tests are smoke/characterization scripts listed in `scripts/verify-production.ts`; the release workflow runs the Stage 36 verification before publishing.

- **Offline tests:** `npm test` runs the `core`, `extensions`, and `ui` groups (the same set as `verify:production`, without typecheck/lint/build). `npm test -- --list` prints them.
- **Lint / format:** Biome, configured in `biome.jsonc`. `npm run lint` (errors and warnings fail) and `npm run format:check` are both part of `verify:production`; run `npm run format` before committing. Rules switched off in `biome.jsonc` carry a reason; keep it that way. The formatter collapses repeated spaces in JSX text, so write aligned text as a string expression: `<Text>{"  ↳ "}{label}</Text>`.
- **Typecheck:** `npm run typecheck` → `tsc --noEmit`
- **Frontend boundaries:** `npm run check:frontend-boundaries` (part of `verify:production`) rejects runtime imports of session internals (QueryEngine, agentic loop, session storage, `state/` stores, plan files, thinking, mailbox, permissions, Bash tool) from `src/ui/` and `src/entrypoint/`; use the SDK instead.
- **Session SDK tests:** `npm run test:sdk` (contract) and `npm run test:interactive-session` (golden for the terminal session flow). RPC mode (`eagent --rpc`, `src/rpc/`) is a thin JSON-RPC layer over the SDK: `npm run test:rpc` drives it over stdio; after changing `src/rpc/protocol.ts` run `npm run rpc:schema` to regenerate `docs/rpc-protocol.schema.json`. ACP mode (`eagent --acp`, `src/acp/`) maps the SDK onto the Agent Client Protocol: `npm run test:acp` drives it with the official `@agentclientprotocol/sdk` client and validates every message against the ACP schema; both modes share the JSON-RPC peer and stdio host in `src/jsonrpc/`. Session-scoped state touched from a test outside a session must run in that session's scope (`runInScopeOf` in `src/sdk/session.ts`).
- **Source hygiene:** `npm run check:source-hygiene` (part of `verify:production`) rejects roadmap stage numbers, development-plan references, reference-implementation pointers, and tutorial wording in `src/` (excluding `src/scripts/`). Legitimate matches go into `ALLOWED_MATCHES` in `scripts/check-source-hygiene.ts` with a reason.
- **Configuration inventory:** `npm run check:config-inventory` (part of `verify:production`) fails when `src/` reads an environment variable, settings key, or `process.argv` flag that the inventory does not list, or when an entry goes stale. Settings keys and environment variables live in `SETTING_CATALOG` and `ENVIRONMENT_VARIABLES` in `src/config/catalog.ts`; argv checks, dynamic env reads, and behavior constants live in `scripts/check-config-inventory.ts`. Run `npm run config:inventory` to regenerate `docs/configuration-inventory.md`.
- **Agent settings:** a runtime resolves the Agent (`src/harness/`) when it starts and installs the snapshot; read Agent settings through `src/harness/active.ts`, never from `process.env` or the settings loaders. Code that has a workspace directory uses `harnessSettingFor(cwd, "<key>")`/`harnessFor(cwd)`: the installed snapshot when the runtime works in that directory, the same Agent resolved for another directory (worktrees), and the directory's settings files when there is no runtime; pass `{ current: true }` for reads outside a model request (session open, turn start, `/config`), which re-read the files without installing the result (and return the installed snapshot when the re-read fails). The runtime's Agent is `default` unless `createAgentRuntime({ harness })` / `--harness` / RPC `initialize` selected another; the resolver installed in `src/sdk/bootstrap.ts` carries that selection, so every read above follows it. `harnessSetting("<key>")` is for code without a directory; without a runtime it sees only the environment and built-in defaults. Environment variables are taken at startup; `refreshHarness()` re-reads the settings files, and the agentic loop calls it before each model request (so one request sees one snapshot) and `AgentRuntime.resolveModel()` before a session picks its model. Tests that change settings files mid-runtime need one of those to run before asserting. The inventory check fails on any read, outside `src/harness/`, of a variable a Harness key resolves. `src/harness/keys.ts` must not import a module that reads the active harness (the import cycle would leave its defaults uninitialized). The Agent's tool lists are applied in `getAllTools()`/`findToolByName()` (`src/tools/index.ts`); take a session's tools from there (or `getToolsForMode`), not from `getRegisteredTools()`, which also returns left-out tools. MCP servers are gated by `mcpServerOffByAgent()` in `src/services/mcp/bootstrap.ts`; a new way to start servers must check it. Single-tool settings (`tools.config`) are read with `toolConfigOf()` from `src/harness/selection.ts`; the Bash and PowerShell limits go through `src/tools/shellToolConfig.ts`, and their `inputSchema` is a getter so the stated default timeout follows the Agent. `npm run test:harness-tools` covers all of it. The Agent's prompt settings (`prompt.identity`, `prompt.sections`, `context.*`) live in `src/harness/prompt.ts` and are applied in `src/context/systemPrompt.ts`; the session prompt context reads the Agent once per turn and passes it to both the static block and the sections, so pass a resolved harness (or leave the key out to resolve one) instead of reading prompt keys elsewhere. `npm run test:harness-prompt` covers them. Skills and sub-agents are selected in their registries (`src/services/skills/registry.ts`, `src/agents/registry.ts`): `findSkill`/`getModelVisibleSkills`/`getAllUserInvocableSkills` and `findAgent`/`getAllAgents` return only what the Agent keeps, and `getRegisteredSkills()`/`getRegisteredAgents()` everything loaded (for views that show what is left out); the prompt passes its resolved harness to them. Compaction reads `compaction.*` in `src/context/compaction.ts`, `src/context/autoCompact.ts` (`isAutoCompactEnabled()`, also checked before reactive compaction in the agentic loop), and `getAutoCompactThreshold()` in `src/utils/tokens.ts`; a session's first task mode comes from `features.tasks` (`src/state/taskModeStore.ts`), and Auto Mode checks `features.autoModeClassifier` before calling the classifier. `npm run test:harness-features` covers these and checks that each feature switch has the same effect from a spec as from its environment variable or setting. Agent definitions are written only through `src/harness/manage.ts` (the SDK's `eagent/sdk/experimental`, RPC `harness/*`, `/harness use`): each change is a locked read-modify-write of `harnesses` (`updateUserSettings` takes a function for that) that resolves every Agent against the new definitions and refuses a change that adds an error. The workspace's default Agent is `harness` in the local settings file of a trusted workspace; `resolveHarness()` without a name picks it (`selectedBy` records it), and `loadWorkspace` binds it by name when the runtime starts. `reloadRuntimeUsing()` in `src/sdk/runtime.ts` reloads the in-process runtime when a change affects its Agent or one it extends. `eagent/sdk/experimental` is `dist/sdk-experimental.js`, a thin entry over `dist/sdk.js` (`src/sdk/sdkEntry.ts` exports `__experimental`), so both share one module instance; a new experimental function goes in `src/sdk/experimental.ts` and in the list in `src/sdk/experimentalEntry.ts` (`test:harness-manage` checks they match). `npm run test:harness-manage` and the `harness/*` checks in `test:rpc` cover it. A session records the Agent it runs with in its `session_meta` record (`harness`: name, hash, and a digest per key; `src/harness/session.ts`). Earlier versions reject unknown record types but ignore extra fields, so the Agent stays a field of `session_meta`: a resume that opens a session with another Agent, changed settings, or no record appends another `session_meta` that repeats the first one's fields, and readers take `harness` from the last one and everything else from the first. `createAgentRuntime({ harness: { session } })` (CLI `--resume` without `--harness`, RPC `initialize`) starts with that Agent: `default` for sessions without a record and when the Agent was deleted or was an inline spec. `resumeSession()` sets `session.harnessCheck`; `/resume` reports the same check in its notice. `npm run test:harness-session` covers it. Every model request goes through `streamMessage()`/`createMessage()` in `src/services/api/streaming.ts` (or opens a `RequestTrace` itself, as the WebSearch adapter does) and passes `trace: { purpose }`; the provider layer calls `trace.sent()` with the body as it goes out (after cache markers; for translated protocols, the Anthropic shape before translation plus `wireBytes`), so a new kind of model request must do the same. `src/trace/requestTrace.ts` measures the parts (no text), keeps the latest record per session scope (`getLatestRequestRecord()`), and links parents through `runInRequestFrame()` (the agentic loop wraps tool execution and reactive compaction in it); `src/trace/traceStore.ts` appends `<sessionId>.trace.ndjson` next to the transcript (not `.jsonl`: earlier versions read every `*.jsonl` as a transcript) when the session persists and `trace.level` is not `off`. The session controller binds the scope with `configureRequestTrace()` and flushes on close. A message's source comes from the table in `src/core/messageSources.ts`: mark a message where the orchestration layer creates it (`markMessageSource()`), and give a new kind of hidden message a prefix `inferMessageSource()` knows, since restored messages carry no mark. A system prompt gets one segment per section only when its text was described with `describeSystemPrompt()` (the session prompt context and sub-agents do). Recording must not change the request: `npm run test:request-trace` checks byte-identical requests with `off` and `summary` and reconciles each record with what the fixture received; `npm run perf:trace` (release gate) checks the 5 ms and 2× budgets. Main-loop requests on the Anthropic protocol are counted beside the request by `src/services/api/tokenCount.ts` (first-party API by default, other endpoints with the profile's `countTokens: true`): parts by difference against a one-message probe, system prompt and tool counts cached by content, an endpoint that rejects counting remembered per model; `RequestTrace.tokenCount()` attaches the result (`tokenCount` on the record, or a later `token_count` line) and the breakdown waits up to 2 s for it, then spreads each part's count over its components. The fixture model answers `count_tokens` with 404 unless a test calls `fixture.countTokens("on")`, so tests against `127.0.0.1` send nothing extra; `npm run test:token-count` covers it. `/context` and `session/context` are built in `src/core/queryEngine/contextBreakdown.ts` from `getLatestMainRequest()` (the record plus the conversation the main loop made it from): while the session's conversation still starts with that conversation, the breakdown is read from the record (`basis: "request"`) and the messages since are added under their sources; otherwise (no request yet, `/clear`, compaction, rewind, resume) it is the estimate (`basis: "estimate"`). Components are the record's segments: a prompt section built from several sources passes its parts (`PromptPart` in `src/utils/promptParts.ts`: rule files, the memory index, skill and sub-agent lines) through `withParts()` in `src/context/systemPrompt.ts`, and `systemPromptLayout()` splits along them. A message that holds text from another source either starts with a known prefix or carries `markLeadingSource()`; a copy made to send (the deferred tool list merged into the first message) takes the original's marks with `copyMessageSource()`. `npm run test:context-coverage` drives every model-visible input and fails on a byte the record does not account for, on text the oracle there cannot place (add the prefix to its `HIDDEN` table and to `USER_PREFIXES`), and on a `MessageSource` no scenario produces.

Most `test:*` commands run files under `src/scripts/`, but **`test:stage30` is the exception**: it runs top-level `scripts/verify-multi-protocol.ts`. ## Gotchas

- **Two similar-looking config dirs are distinct:**
  - `.claude/` (`skills/`, `agents/`, `commands/`) — Claude Code integration config
  - `.easy-agent/` (`skills/`, `agents/`, `commands/`, `settings.json`) — Easy Agent's own runtime config
  Do not merge them or move files between them.
- **`step/` is intentional tutorial code**, not a build artifact. It holds milestone snapshots (`step1.js` … `step35.js`) that mirror implementation stages; do not delete or clean it up.
- **`dist/` is generated and ignored by git**. Rebuilding with `npm run build` replaces it with the single-file release artifact and sourcemap.
- **Secrets/config caution:** `.env` and `.easy-agent/settings.json` may contain local provider settings or secret-looking values. Do not copy token values into docs or output.
- **README is the product entry.** The release gate rejects roadmap stage progress or `step/` snapshot links in `README.md` / `README.zh-CN.md` and checks that every relative link resolves. The milestone table lives in `docs/learning-path.md` and `docs/learning-path.zh-CN.md`.
- **No `CONTRIBUTING.md`**; per the README, external contributions are not accepted yet, so conventions may shift.
- **Multi-provider model config** lives in user/project `settings.json`:
  - Anthropic provider names pass through directly
  - Other providers use `protocol` + `baseURL` + `${ENV_VAR}` interpolation for API keys
  - Relevant env vars: `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `OPENAI_API_KEY`, `GEMINI_API_KEY`, `WEB_SEARCH_API_KEY`
- **Notable CLI flags:** `--print` (headless JSON output), `--plan`, `--auto`, `--dump-system-prompt`, `--model <name-or-profile>`.
